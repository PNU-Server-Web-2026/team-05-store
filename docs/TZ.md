# Технічне завдання. Online Store / Warehouse API

Дисципліна: «Серверне вебпрограмування» | Команда: team-05-store | Тривалість: семестр, 9 лабораторних робіт (спринти S1–S9) | Стек: ASP.NET Core 10, EF Core 10, PostgreSQL 17, SignalR, xUnit, Docker

## 1. Загальний опис

Потрібно розробити серверний застосунок (REST API, Application Programming Interface) для інтернет-магазину з кількома складами, що забезпечує ведення каталогу, облік залишків на складах, оформлення замовлень з резервуванням товару та керування їх життєвим циклом. Клієнтська частина (вебсайт чи мобільний застосунок) не розробляється: взаємодія з системою здійснюється через HTTP API, документоване за стандартом OpenAPI. Платіжна система не підключається: оплата фіксується статусом замовлення.

Проєкт виконується командою з 5–7 студентів в одному репозиторії. Кожен студент виконує власні задачі з дошки GitHub Project, а система в цілому повинна працювати як єдине ціле. Предметна область обрана навмисно: складський облік — класичний приклад, де коректність залежить не лише від коду контролерів, а й від моделі даних, транзакцій та поведінки системи при одночасних запитах.

Наскрізний принцип роботи: предметна область -> модель даних -> REST-контракт -> реалізація -> тести -> розгортання.

## 2. Предметна область

### 2.1. Ролі користувачів

- **Покупець (Customer)** — переглядає каталог, оформлює, оплачує та скасовує власні замовлення, застосовує промокоди.
- **Менеджер магазину (Manager)** — керує каталогом, складами, постачальниками і залишками, змінює статуси замовлень, переглядає звіти.
- **Адміністратор (Admin)** — має права менеджера і, крім того, керує обліковими записами та ролями користувачів.

Анонімний користувач може переглядати категорії і каталог активних товарів, але не може оформлювати замовлення.

### 2.2. Сутності

| Сутність | Основні поля | Особливості |
|---|---|---|
| Категорія (Category) | назва, slug у форматі lowercase-kebab-case (наприклад, smart-phones), опис, батьківська категорія | slug унікальний; категорії утворюють дерево; довідник кешується |
| Товар (Product) | назва, артикул SKU (Stock Keeping Unit; A–Z, 0–9, дефіс), ціна, опис, ознака активності | SKU унікальний; 0 < ціна ≤ 1 000 000, до 2 знаків після коми; знятий з продажу товар не видаляється фізично (soft delete) |
| Покупець (Customer) | ім'я, прізвище, email, телефон у форматі E.164, адреса доставки | email унікальний; профіль пов'язаний з обліковим записом |
| Склад (Warehouse) | назва, місто, адреса, пріоритет 1–100 | назва унікальна; пріоритет задає порядок резервування |
| Постачальник (Supplier) | назва, код ЄДРПОУ (Єдиний державний реєстр підприємств та організацій України — рівно 8 цифр), email, телефон | код ЄДРПОУ унікальний |
| Залишок (Stock) | товар, склад, кількість (Quantity), зарезервовано (Reserved), мінімальний залишок (MinQuantity) | ключ «товар + склад» |
| Рух товару (StockMovement) | товар, склад, тип (Receipt, WriteOff, TransferIn, TransferOut, Sale, Return), кількість, дата, причина | журнал лише доповнюється |
| Замовлення (Order) | покупець, статус, дата створення, сума (Total) | суму рахує сервер |
| Позиція замовлення (OrderItem) | замовлення, товар, кількість, ціна за одиницю (UnitPrice) | ціна фіксується в момент оформлення замовлення |
| Промокод (PromoCode) | код, знижка (1–50 % або фіксована сума), період дії, ліміт і лічильник використань | код унікальний |

### 2.3. Зв'язки

Категорія і постачальник містять багато товарів (1:N); категорію з товарами видалити не можна (Restrict), а при видаленні постачальника посилання в товарах обнуляється (SetNull). Категорії утворюють дерево через самопосилання. Покупець має багато замовлень, замовлення — багато позицій (1:N). Товар і склад пов'язані через залишок, що несе власні дані (кількість, резерв, мінімум), тому моделюється окремою сутністю, а не простим зв'язком M:N (багато-до-багатьох).

### 2.4. Бізнес-правила

1. Доступний залишок дорівнює Quantity − Reserved; у базі даних діють check-обмеження Quantity ≥ 0 і 0 ≤ Reserved ≤ Quantity.
2. Замовлення оформлюється лише тоді, коли всі товари активні і є в потрібній кількості (сумарно по складах); інакше повертається 409 з переліком товарів, яких бракує. Замовлення містить не більше 50 позицій (параметр MaxItemsPerOrder).
3. При оформленні товар резервується: Reserved збільшується на складах у порядку пріоритету (першим — склад із меншим Priority). Усе виконується в одній транзакції: або замовлення створено повністю, або нічого не змінилось.
4. Остання одиниця товару не може бути продана двічі навіть при одночасних запитах. Перевірки в коді C# для цього недостатньо — гарантія забезпечується засобами PostgreSQL: оптимістичною конкурентністю на Stock (xmin) з повтором до 3 спроб або блокуванням SELECT … FOR UPDATE; вибір обґрунтовується в Pull Request.
5. Статуси замовлення: New -> Paid -> Shipped -> Delivered; зі стану New або Paid можливе скасування (Cancelled). Інші переходи заборонені і повертають 409. При скасуванні резерв повертається; при відвантаженні (Shipped) Quantity і Reserved зменшуються і створюється рух типу Sale.
6. Неоплачене замовлення (New) автоматично скасовується через 24 год (параметр UnpaidOrderTimeoutHours) з поверненням резерву; перевірка виконується щогодини.
7. Надходження, списання і переміщення фіксуються в журналі руху; переміщення між складами — дві операції в одній транзакції. Залишок не може стати від'ємним (409); залишок у Stock завжди узгоджений із сумою записів руху.
8. Прострочений або вичерпаний промокод повертає 400. Знижка не робить суму замовлення від'ємною; лічильник використань збільшується в тій самій транзакції.
9. Категорія не може стати нащадком самої себе (400). Видалення категорії, що має дочірні категорії або товари, повертає 409.
10. Покупець бачить і скасовує лише власні замовлення; неактивні товари покупцям не показуються.

Числові значення параметрів (24 год, 50 позицій) задаються в конфігурації і не записуються в коді як «магічні числа».

### 2.5. Основні сценарії

- перегляд дерева категорій і каталогу з пошуком, фільтрами і сортуванням;
- надходження, списання і переміщення товару між складами;
- оформлення замовлення з резервуванням і промокодом;
- оплата, відвантаження, доставка, скасування замовлення;
- сповіщення в реальному часі: покупцю — про статус замовлення, менеджерам — про низький залишок;
- фотографії товарів, експорт замовлень у CSV (Comma-Separated Values), імпорт прайс-листа з CSV;
- звіти про низькі залишки і продажі за категоріями.

## 3. Функціональні вимоги

### 3.1. Обов'язковий мінімум (MVP)

Мінімум (MVP — Minimum Viable Product), без якого система не вважається працездатною і командна частина оцінки не зараховується:

- CRUD (створення, читання, оновлення, видалення) категорій, товарів, покупців, складів і постачальників з валідацією, пагінацією та зберіганням у PostgreSQL;
- залишки товарів на складах і журнал руху товарів;
- оформлення замовлення з резервуванням і захистом від продажу останньої одиниці двічі;
- статуси замовлення;
- реєстрація, вхід (JWT — JSON Web Token) і розмежування доступу Customer / Manager / Admin;
- запуск усієї системи командою `docker compose up`;
- наскрізний демонстраційний сценарій (розділ 7), реалізований як інтеграційний тест.

### 3.2. Додатково

Дерево категорій, промокоди, автоскасування неоплачених замовлень, звіти, сповіщення SignalR, робота з файлами, кешування, rate limiting, публікація Docker-образу. Ці функції не обов'язкові для MVP, але саме вони дають більшість балів за складні задачі.

## 4. Розбивка на етапи (рекомендована послідовність дій)

Кожна лабораторна робота — окремий спринт (milestone на GitHub). Нижче наведено, що має працювати наприкінці спринту. Конкретні задачі з кроками виконання — на дошці команди.

- **ЛР1 (S1). Проєкт та HTTP API.** Налаштувати документацію API, health checks, конфігурацію (Options pattern), CORS; погодити ERD-діаграму (Entity-Relationship Diagram) предметної області.
- **ЛР2 (S2). REST-контракт.** Описати DTO (Data Transfer Object) і контролери для категорій, товарів, покупців, складів і постачальників; реалізувати сервіси в пам'яті; додати валідацію; налаштувати інтеграційні тести на PostgreSQL (Testcontainers).
- **ЛР3 (S3). EF Core і PostgreSQL.** Створити сутності, конфігурації й міграції; замінити in-memory сервіси на EF Core без зміни тестів; додати seed-дані, унікальні індекси та check-обмеження; підготувати Docker Compose для розробки.
- **ЛР4 (S4). Складніша модель даних.** Реалізувати зв'язки 1:N, дерево категорій, залишки, замовлення з позиціями, пагінацію, фільтри і пошук, soft delete, аудит змін, оптимістичну конкурентність; усунути N+1.
- **ЛР5 (S5). Бізнес-логіка.** Реалізувати доменні помилки, кешування категорій, журнал руху, резервування при оформленні, захист останньої одиниці, статуси замовлення, промокоди, автоскасування, звіти.
- **ЛР6 (S6). Middleware і помилки.** Єдина обробка помилок (ProblemDetails), correlation ID, структуроване логування, rate limiting, output caching каталогу товарів.
- **ЛР7 (S7). Автентифікація й авторизація.** Реєстрація, JWT, refresh-токени, ролі, профіль покупця, доступ лише до власних замовлень, тести авторизації.
- **ЛР8 (S8). SignalR, файли, тести.** Хаб сповіщень, події про замовлення і залишки, фотографії товарів, експорт і імпорт CSV, звіт покриття тестами.
- **ЛР9 (S9). Docker і фінальний захист.** Dockerfile, повний docker-compose з міграціями, публікація образу, демонстраційний сценарій, фінальна документація.

Задачі одного спринту не обов'язково закривати до його завершення, однак відставання більше ніж на один спринт свідчить про проблеми в команді і розглядається на занятті.

## 5. Технічні вимоги та критерії приймання

- Код організовано за функціональними зрізами: кожна функція — в окремій папці `Features/<Назва>/` (контролер, DTO, сервіс, реєстрація залежностей).
- Контролери працюють лише з DTO; сутності бази даних назовні не віддаються.
- Бізнес-правила реалізуються в сервісах, а не в контролерах; помилки повертаються у форматі ProblemDetails з коректними статус-кодами (400, 401, 403, 404, 409, 429).
- Усі операції з базою даних асинхронні; читання — без відстеження змін (AsNoTracking) і з проєкцією в DTO.
- Зміни моделі даних супроводжуються міграцією в тому ж Pull Request.
- Секрети (паролі, ключ JWT) не зберігаються в репозиторії.
- Кожна задача має тести; інтеграційні тести виконуються на справжньому PostgreSQL.
- Збірка без попереджень (TreatWarningsAsErrors), CI зелений.

Задача вважається виконаною лише після злиття Pull Request у гілку dev і короткого усного захисту. Наявність коду без розуміння його роботи не є підставою для зарахування балів.

## 7. Демонстраційний сценарій і захист

На фінальному занятті команда демонструє систему за сценарієм: перегляд каталогу -> замовлення з резервуванням -> одночасна купівля останньої одиниці (успішна лише одна) -> оплата -> відвантаження -> залишок на складі зменшився -> менеджери отримали сповіщення про низький залишок. Окремо демонструється тест, у якому з 10 паралельних замовлень на 1 одиницю товару успішне рівно одне, решта отримують 409.

Кожен студент на підсумковому захисті пояснює власні задачі: яку проблему вони розв'язують, як реалізовані, як перевірені і що станеться при некоректних вхідних даних.

## 8. Організація роботи

Правила роботи з гілками, Pull Request, міграціями та дошкою задач наведені в `CONTRIBUTING.md` репозиторію; загальні правила курсу й оцінювання — у репозиторії `server-web-common`. Використання генеративного ШІ допускається, однак студент повинен пояснити кожен рядок власного коду.
